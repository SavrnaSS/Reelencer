Linked-account statistics run independently of page visits. Apply `202610250001_background_social_sync.sql` and configure an authenticated POST to `/api/jobs/social-sync` every minute using the server's `CRON_SECRET` bearer token. The existing Cloudflare email worker includes this Cron Trigger: set its `CRON_SECRET` to the application's secret and deploy the worker after deploying the updated application. `SOCIAL_SYNC_URL` must point to the application's HTTPS job endpoint. An existing external scheduler can call the same endpoint instead. Do not use a URL that redirects.

Local `next dev` starts a once-per-minute background loop automatically through `instrumentation.ts`. Set `SOCIAL_SYNC_IN_PROCESS=false` to disable it, or explicitly set it to `true` on a long-running production Node host. Serverless production requires external cron. `npm run social:sync` processes a bounded batch immediately; `npm run social:check` reports connection health and the last completed scheduler heartbeat, without revealing credentials. The admin card distinguishes an active scheduler from a missing/stale heartbeat. A healthy heartbeat means the queue is running, not that every provider request succeeded.

Instagram accounts are due every five minutes; YouTube accounts every thirty minutes. The scheduler claims the oldest deadlines directly from all active linked accounts with PostgreSQL `FOR UPDATE SKIP LOCKED`, avoiding list-page limits or starvation. Two accounts run concurrently, up to twelve per invocation within a bounded time budget. Queue capacity depends on provider latency; large backlogs drain over subsequent minute ticks. Claims expire after two minutes if a process crashes. Lease tokens prevent a late completion from overwriting a newer account sync state. Paused, unlinked and unconfigured platforms are excluded. Visible account sections also check due work as a fallback, sharing these same claims. Plain GET requests are read-only; only explicit `sync=1` requests check providers.

Network failures retry from two minutes, login walls and rate limits from thirty minutes, and credential errors from one hour. Explicit profile-absence observations use the five-minute confirmation flow described below. Other consecutive failures increase the delay up to six hours with stable account jitter; platform `Retry-After` values are respected up to twenty-four hours. A failed attempt updates `last_sync_attempt_at`, never `last_synced_at` or saved measurements. Both dashboards display the last successful update, next check/retry, connection source, and actual progress rather than presenting a failed attempt as fresh data. Manual requests have a one-minute cooldown and cannot steal leases, sync paused accounts or bypass a platform rate-limit deadline. New connection settings enqueue waiting accounts for recovery.

When a Meta access token and the managing Instagram professional account ID are configured, the reader uses the official [Business Discovery API](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/business_discovery) first. The returned username must match the linked handle. This API supports eligible public professional accounts, not arbitrary private or personal accounts. Credentials are sent in an Authorization header and stored encrypted when entered in the console. A connection test must pass before the console saves them. Discovery supplies profile counts and available media likes/comments; it does not expose another account's private reach, saves, shares or reel views. Up to two author-verified public reels supplement views within the same request budget, preserving public provenance for view measurements.

Without API credentials, Instagram reads its public `https://www.instagram.com/{handle}/` page. A login redirect or unreadable main page gets one bounded public `/{handle}/embed/` fallback; a rate limit does not trigger extra requests. API connection errors can fall back to public reads, while quota errors stop further traffic. Public reads remain conditional on what Instagram exposes. No implementation can guarantee private metrics or overcome a platform login wall without appropriate authorization.

The reader checks the requested handle against embedded profile data or page metadata. Embedded JSON gives exact counts when exposed; metadata can provide abbreviated, rounded follower/following/post counts. Up to 25 exposed posts are deduplicated by shortcode. Known posts receive only available views/likes/comments; new dated posts after linking enter the existing review queue. Undated posts are never automatically added for payment.

Profile reads are saved with `source = 'profile'` and an explanatory snapshot note. Apply `202610080006_instagram_profile_sync.sql` before running this code. YouTube retains its API reader and screenshot insights retain their own provenance.

Login redirects, rate limits, missing profiles and unreadable pages produce a sync error without replacing existing metrics. Requests use a fixed Instagram origin, reject redirects, time out after eight seconds and cap HTML at 4 MB. Private profiles expose only available public counts. Hidden metrics are omitted, never guessed or filled with zero. Public pages frequently expose counts without any post data, so automatic post discovery is conditional on the page's content.

Public pages do not supply this application's reach, profile visits, saves or shares. Use the screenshot reader or manual check-ins for those insights. No stored Instagram passwords, login cookies or private endpoints are used by the public profile reader.

Public reel embed pages are checked first for ServerJS `contextJSON` data, parsed as JSON without executing JavaScript. A matching owner and shortcode are required. If the embed exposes a view count (including zero), no extra post request is needed. When it exposes no views, the primary page provides a bounded fallback; login redirects and rate limits stop extra requests. Individual reel pages are checked for embedded media JSON, verified JSON-LD InteractionCounter records, and canonical Open Graph descriptions. Every accepted metric must match the requested shortcode and creator. Public Reels-tab and profile links provide discovery where available; existing tracked reel URLs also work when the profile exposes no links. Up to six reels are checked in batches of two within the shared eight-second request budget. Older tracked-post updates are prioritized so larger lists rotate over successive syncs. Post-page failures preserve the profile counts and previous post metrics. The snapshot note reports unreadable post pages. The admin summary shows tracked reel views and likes separately from reach and only totals metrics actually present.


Apply `202610080008_reel_view_freshness.sql` for view measurement timestamps and provenance. View timestamps update only when views are actually present; a likes update or review never refreshes them. Claims freeze this measurement source and time rather than a generic post update. The creator headline shows total measured non-rejected reel views and coverage; cards and tables always display Views, distinguishing unavailable counts from zero. These are the latest counts exposed by Instagram at a five-minute polling cadence, not a guaranteed instantaneous feed for every reel. Instagram may cache public embeds or hide their metrics.


New-reel discovery runs during scheduled and page-initiated public profile syncs, including when reels are already tracked. The public profile embed exposes a dated timeline on many accounts whose main profile HTML has no feed. Its media is merged without overwriting the main profile counts. The Reels tab is also checked even when the profile feed contains older or pinned reels, so uploads omitted from that feed can still be found. Discovery reads have separate short deadlines within the shared eight-second budget. At most six reels are checked with two concurrent page reads; new eligible links reserve at least two slots when the tracked list is full, and one saved-reel slot rotates across larger lists. Submitted reels missing counts are prioritized among tracked URLs. Verified page permalinks retain their reel type even when an embed omits the video flags. Old dated posts and photos do not consume new-reel slots. A new embed that exposes views but no date also loads the primary reel page to verify publication before insertion. Undated and unrelated reels stay unimported.

New owned reels within the existing linking window are inserted canonically as submitted, with automatic discovery provenance. Existing URL uniqueness and shortcode matching make repeated reads idempotent and preserve prior approvals/rejections. The creator cards and table label automatically found reels; discoveries made while the section is open show an accessible notice with a Show newest action, without changing the creator's current sort or filter. Private, cached or blocked public pages can delay discovery; this reader does not paginate Instagram's private feeds.

The visible Accounts section checks server sync deadlines every thirty seconds as a fallback; platform reads remain limited to each account's persisted cadence and error backoff. Saved metrics arrive through private realtime invalidations, with polling when realtime is unavailable.

Submitting a reel link reads that specific public reel immediately, independently of the account sync cooldown. Instagram share links and permalink variants are normalized to one canonical URL and shortcode. Only matching-author/shortcode counts are accepted, including measured zero. Public captions and actual publication dates fill the record where exposed. Unavailable or blocked reads still save a pending review record with the creator’s fallback details; the next scheduled or page-initiated sync retries it without replacing saved numbers with missing values.

Submissions reuse an existing record before checking the pending queue limit and recover a concurrent discovery insert through URL uniqueness. Refreshed metrics preserve existing approvals, rejections and submission provenance. The API returns the saved post and a status message. Card headlines, performance ranks and charts compare one shared metric across reels. If views are selected, a reel missing views is not ranked or shown with likes/comments as a substitute; a measured zero remains visible as zero.


## Tracking window

Reels count from the day their account was linked, in India time (`lib/reelTracking.ts`; `public.reel_tracking_start` in the database). A reel that went live earlier on the linking day counts; one from any earlier day doesn't. Apply `202610290001_reel_tracking_window.sql`.

- **Sync:** discovery only adds reels dated inside the window, and reels dated before it are never refreshed. If an undated reel waiting for review turns out to predate linking, sync records its date and rejects it with the note "Posted before this account was linked."
- **Submissions:** creators can't submit, and admins can't add or approve, a reel from before the linking day (`reel_before_link`). The date pickers start at the linking day.
- **Database:** a trigger blocks approving a pre-link reel or moving an approved reel's date before the window. The migration rejects pending pre-link reels with the same note. View payout quotes and claims leave out pre-link reels, including ones approved before this rule existed. Undated reels stay eligible and are flagged for a check.
- **Creators never see pre-link reels.** The creator API drops them (`listCreatorAccounts`, the creator's "Sync now" and profile-recovery responses), as does the device cache (`creatorAccountData`). Creator reel lists, charts, top reel, totals, earnings and posting progress therefore come only from reels that can be paid. Resubmitting a pre-link reel's link is refused rather than returning the saved record.
- **Account statistics:** each sync's period views (`impressions`) are the views gained on tracked reels since the last sync, plus the views of newly found ones. The snapshot's `total_views` is the sum over tracked reels. Account-wide totals such as a YouTube channel's lifetime views are no longer used, because they include older videos. Followers, following and post count remain profile-level figures. Snapshots saved before this change keep their original values.
- **Screenshots:** the screenshot reader matches and updates only reels inside the window.
- **Admins** still see every reel, with pre-link ones in the **Before linking** tab for auditing. Admin totals and earnings ignore them.
- **Admin reel list:** the panel states the tracking start date. Tabs (All tracked, To review, Approved, Rejected, No date, Before linking) show counts. The list can be searched by caption or link, filtered by source (sync, creator, team) and posting date (7 or 30 days), and sorted by review state, date, views, likes or last update. It shows totals for the current view, bulk-approves the reels shown and exports them as CSV.

## Removing a reel

Apply `202610290002_reel_removal.sql`. In the admin reel list, ✕ asks for confirmation and an optional team-only reason, then removes the reel from Reelencer. Removal keeps the row as a tombstone (`removed_at`, `removed_by`, `removal_reason`) instead of deleting it, so that:

- **Creators never see it.** It's dropped from every creator response and from the creator's cached data, so it disappears from Linked, charts, totals, top reel, earnings and posting progress.
- **It never counts.**
  - A removed reel is always `rejected`, and a database trigger (`reel_removed`) blocks approving or re-queuing it, so it's never approved, waiting or payable.
  - View quotes and claims leave it out.
  - Pending claims that cite it can no longer be approved as they are; the admin is told how many there are.
  - The admin overview's reel activity and review queue, admin totals and the account list's "to review" counts skip it.
- **It can't come back.**
  - Sync still recognises the reel, so it never re-discovers it or refreshes its numbers.
  - A creator resubmitting the link is refused.
  - An admin re-adding the same link is pointed to Restore.
  - The screenshot reader skips it.

Removed reels wait in the admin's **Removed** tab with who removed them and why. **Restore** brings a reel back to **To review** so it's checked again; the tracking window still applies. Views already paid through approved claims stay in payout history. Creators withdrawing their own unreviewed submission is unchanged.

## Missing profiles and recovery

Apply `202610270001_social_profile_recovery.sql`. A linked profile is removed from the creator’s active Linked list only after two explicit profile-level not-found observations at least five minutes apart. A direct Instagram profile 404/410 or an empty, successful YouTube handle lookup can supply that evidence. Individual reel errors, login walls, private profiles, rate limits, malformed replies, credential failures and an ineligible Meta Business Discovery lookup cannot remove an account. A successful profile read clears earlier suspicion. For a platform that cannot be read automatically, admins can use **Profile not found?**, confirm that they opened the real profile and found it unavailable, and send the same recovery prompt. Existing ambiguous not-found failures are queued for a fresh check by the migration; it does not unlink any account.

The account row becomes `unlinked` with `profile_health.status = 'missing'`. Reels, review decisions, measurements and payout history are retained. Its saved approved earnings remain in the creator’s earnings summary. A separate recovery card appears in Accounts, with a dashboard notice and navigation badge elsewhere. Plain manually unlinked accounts do not expose self-service recovery.

Creators can correct the username and matching profile URL, put the supplied code in the profile bio and choose **Verify profile**. The server requires the code in the profile’s own biography or YouTube channel description; a code somewhere else on a page is insufficient. Known platform identities must match, so a different account cannot inherit historical work. Blocked reads or unsupported automatic readers create a manual verification request. The admin **Profile verification** filter shows these records; the reviewer opens the requested profile, confirms the code, and restores it. The ordinary Active status selector cannot bypass this check. A corrected account keeps its original row and resumes scheduled statistics checks.

Checks have a one-minute cooldown. Recovery attempts are claimed before network reads and saved with compare-and-set protection. The database restoration function serializes competing restores, checks the worker, current request, duplicate handles and account limits, and is executable only by the service role. Administrator confirmations must match the latest submitted recovery request.

Additional-account requests whose profile is explicitly absent are returned as **Changes needed**, reopening the creator’s correction form. Such a request cannot be approved until its profile check is corrected; a login-blocked read remains a manual-review warning.
